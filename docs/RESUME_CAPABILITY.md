# 重開後續跑：行為與各流程的續跑能力盤點（#151）

> 決策：`docs/adr/0001-long-running-tasks-after-window-close.md`（方案 C：只做重開後續跑，**不得自動繼續**）。
> 驗證清單：`docs/WINDOWS_VERIFICATION.md` 第 3 節。

## 核心觀念：快取是續跑的依據，checkpoint 是「沒做完」的標記

1. 每批翻譯完成後的順序是：**快取存檔（fsync）→ 輸出檔寫入 → checkpoint 寫入（原子寫入＋fsync）**。
   checkpoint 永遠最後寫，所以它不會領先已落盤的譯文。**只有快取 durable 之後才算完成的批次**：
   快取存檔失敗或該批項目被快取拒絕時，輸出檔仍會寫出，但**不寫 checkpoint**，任務以 FAILED 結束；
   checkpoint 維持上一個 durable 批次的狀態，重開後只會重翻沒有 durable 的那一批。
2. 重開後，翻譯照常抽取輸入並做**快取分流**：已完成批次的譯文是快取命中，直接寫回輸出；
   只有未完成的項目才送 API。**續跑不依 checkpoint 的位置跳過任何項目**——
   舊實作會用 `items[completed:]` 跳過前面的項目，當快取沒有同步（例如關閉快取儲存）時，
   已翻譯的內容會變回原文（漏翻）。這個路徑已移除，並有端到端測試鎖住。
3. checkpoint（`data/logs/translation_checkpoint.json`，版本 2）記錄：輸入／輸出資料夾、`export_lang`、
   `write_new_cache`、已處理／總數（僅供顯示）、**涵蓋全部抽取項目的指紋**、更新時間。
   指紋不受快取進度影響，所以重開後仍能比對；輸入內容或來源不同、舊格式都會被判為無法續跑。
4. `translator.enable_cache_saving = false` 時不寫 checkpoint（沒有可還原的來源）；殘留的舊標記會在下次翻譯時
   明確警告並捨棄。

## 兩種「進度」不要混為一談

| 名稱 | 來源 | 語意 |
|---|---|---|
| `TranslateLoopResult.processed`（以及 UI 的進度條、完成訊息） | 本次行程 | 這次執行**已處理**的項目數，包含剛翻譯完、但快取存檔失敗而尚未 durable 的批次 |
| checkpoint 的 `completed_count`（對話框顯示的「已保存的進度」） | 磁碟上的標記 | **已 durable、可恢復**的進度：只有快取存檔成功的批次才會寫入 |

例如：第 1 批 durable、第 2 批 API 成功但快取存檔失敗 → 任務以 FAILED 結束，`processed = 4`，
checkpoint 仍是 2（即第 1 批）。重開後依 checkpoint 與快取，只會重翻第 2 批。
UI 與文件說明「可恢復的進度」時一律以 checkpoint 為準，不用 `processed`。

## 標記何時建立與清除

- **建立**：第一個批次的快取 durable 之後才寫第一次 checkpoint（之後每批更新）。
  所以「第一批完成之前就被強制結束」不會有標記，重開後也不會提示上次的任務——這時沒有任何
  已完成的內容可以續跑，直接重新開始即可。
- **更新**：每批「快取存檔成功 → 輸出寫入 → checkpoint」；快取失敗的批次不寫。
- **清除**：完整完成（`DONE` 且全部處理完）、所有項目都由快取命中、使用者選「放棄」。
  取消、失敗、金鑰耗盡都保留。
- **損毀的標記**（無法解析，或內容不是 JSON 物件）：記錄警告並改名為
  `translation_checkpoint.json.corrupt`（保留供診斷，下一個損毀的檔案會覆蓋它），視為沒有標記；
  不會殘留在原位而在每次啟動重複警告。

## 啟動流程

| 步驟 | 行為 | 是否呼叫 API |
|---|---|---|
| 啟動偵測 | `lm_resume.peek_interrupted_task()` 讀 checkpoint（唯讀） | 否 |
| 對話框 | 顯示輸入／輸出資料夾與進度；背景執行緒比對輸入指紋（`check_resume_feasibility`，會讀輸入資料夾） | 否 |
| 續跑 | 僅在檢查通過後可按；切到機器翻譯頁，帶入上次的輸入與選項（dry-run 一律關閉）並開始，與按下「開始翻譯」相同 | 使用者按下後才會 |
| 放棄 | `clear_checkpoint()`；已翻譯內容仍保留在快取 | 否 |
| 稍後再說 | 什麼都不做，下次啟動再詢問 | 否 |
| 指紋不符／輸入資料夾不存在／舊格式 | 顯示原因，「續跑」停用，只能放棄或稍後；**不會靜默忽略** | 否 |

使用者做出選擇之前，不會啟動任何翻譯。

標記在「取消、失敗、金鑰耗盡、被關閉或強制結束」時都會保留（只有完整完成才清除），所以使用者主動取消過的任務，下次啟動也會被詢問；選「放棄」即可清除。

## 各流程的續跑能力盤點

| 流程 | 續跑機制 | 本次是否提供「重開後詢問續跑」 | 備註 |
|---|---|---|---|
| 機器翻譯頁（`translate_directory_generator`） | 翻譯快取（每批 fsync）＋ checkpoint 標記 | **是** | 中斷點（剛開始／批次之間／快取落盤後 checkpoint 前）都有端到端測試 |
| 一鍵流水線的翻譯步驟 | 同上（逐來源呼叫同一個函式） | 否 | 全域只有一個 checkpoint：上一個來源完成就清除，下一個來源再建立。中斷後重跑流水線，已完成部分由快取命中，很快跑完 |
| FTB／KubeJS／MD 翻譯 | 翻譯快取（共用批次迴圈）＋ `translator_<kind>_checkpoint.json` 標記（版本 2） | **是**（#164） | 見下方「FTB／KubeJS／MD 的續跑」 |
| 語系合併 | 無 | 否 | 沒有續跑機制；重開需重跑（輸出可重新推導） |
| JAR 提取 | 無 | 否 | 同上 |
| 打包 | 無，但 staging 是增量更新（#158） | 否 | 重跑成本低 |

## FTB／KubeJS／MD 的續跑（#164）

沿用機器翻譯頁的設計：快取是續跑依據、標記只是「任務沒做完」的記錄與重新執行所需的選項。差異與決定：

| 問題 | 決定 |
|---|---|
| 標記範圍 | **整個任務**一個標記（`data/logs/translator_<kind>_checkpoint.json`，`kind` 為 `ftbquests`／`kubejs`／`md`）。FTB 是逐檔案翻譯、每個檔案一個翻譯迴圈，迴圈完成（DONE）只回報給任務，**整個任務完成才清除標記**；取消、失敗、有迴圈沒 DONE 都保留 |
| 續跑做什麼 | **以同一組選項重新執行整條流程**（輸入／輸出資料夾、各步驟開關、`write_new_cache`，MD 另有 `lang_mode`）。抽取、清理等步驟會從輸入重新推導；翻譯步驟由快取命中已完成的部分，只翻剩下的；注入步驟照常執行。續跑一律是正式執行（dry-run 關閉、翻譯步驟開啟）。MD 中斷在哪一步都一樣：因為前面的步驟可重新推導，不需要記錄「跑到哪一步」 |
| 輸入指紋 | 流程**實際會讀取的來源檔案內容**的 SHA-256（不用 mtime）：FTB＝`config/ftbquests/quests` 底下的 `.snbt`／`.json`；KubeJS＝kubejs 目錄底下的 `.js`／`.json`；MD＝路徑含 `en_us`／`zh_tw` 的 `.md`。輸出資料夾（預設 `<輸入>/Output`）一律排除，流程自己寫的檔案不會讓指紋改變。在任務開始時（背景執行緒）計算一次 |
| 指紋成本 | 來源超過 50,000 個檔案或 512 MB 時**不提供續跑**（不寫標記，翻譯本身不受影響），避免輸入選到整個 modpack 時花很久雜湊。對話框的檢查在背景執行，先顯示「檢查中」 |
| 啟動對話框 | 一個對話框列出**全部**未完成的任務（機器翻譯、FTB、KubeJS、MD），每個任務各自「續跑」「放棄」；底部「稍後再說」。**一次只續跑一個**（避免同時搶快取與金鑰額度），續跑某個任務後對話框關閉，其餘任務的標記保留，下次啟動再詢問；放棄只清除該任務 |
| 續跑的入口 | 機器翻譯回到機器翻譯頁；FTB／KubeJS／MD 回到任務翻譯頁並切到對應分頁（`TranslationView.resume_interrupted`），帶入上次的輸入與選項後開始 |
| 舊格式標記 | 先前由 `JsonCheckpointAdapter` 寫的舊格式檔案（沒有版本與輸入資料夾，從來沒有程式讀取），以及 `kind` 不符、缺少輸入資料夾的標記，**不會被靜默忽略**：啟動對話框會列出該任務，顯示「無法續跑：舊版續跑標記缺少來源與版本資訊，無法安全續跑；請放棄此任務」，「續跑」停用，只能放棄（清除）或稍後。新任務開始寫入時會直接以版本 2 標記取代舊檔 |
| 進度顯示 | 對話框的「已保存的進度」取自標記：`completed_count` 是已 durable 的累計處理數，`total` 是該次執行的待翻譯總數（FTB 為全域待翻譯數；續跑後因快取命中而變小）。僅供顯示，不影響續跑 |

沿用 `translator_<kind>_checkpoint.json` 這個檔名，但**內容契約改變**：舊版寫入專用（沒有任何程式讀取）的格式不再由服務層產生；檔案存在時必定是版本 2 續跑標記，會被偵測、驗證、放棄與續跑實際使用。只有在沒有任務的情況（CLI 或測試直接呼叫 `JsonCheckpointAdapter`）才維持舊格式，服務層不會走到。有 `resume_task`（服務層包住整個任務）時 `clear()` 只回報「這個迴圈完成」。

## 已知限制

- 「剛開始、第一批尚未 durable」就中斷時沒有標記，也沒有已完成內容；直接重新開始即可（見上方「標記何時建立與清除」）。
- 被中斷批次內「已回傳但尚未寫入快取」的項目會重新翻譯（最多一批）。
- FTB／KubeJS／MD 續跑會重新執行抽取與清理步驟（輸入很大時需要一點時間）；只有翻譯結果由快取還原。
- 以 `untranslated`（批次縮到極限而回填原文）收尾的項目不寫入快取，續跑時會再試一次。
- 關閉視窗時任務確實會停止（PR #149 的確認、取消、flush 為緩解）；打包 exe 後關閉不保證執行任何清理，
  所以落盤都在每批完成時完成，不依賴關閉流程。
