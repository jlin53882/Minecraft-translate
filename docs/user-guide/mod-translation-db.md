# Mod 翻譯資料庫（Translation DB）

分版本的翻譯記憶庫（SQLite）：掃描 mods 資料夾的 jar 建立、機器翻譯時優先查詢並把結果寫回、可在介面手動校對。
與「翻譯快取」並存、互不取代：快取記錄「AI 翻過這句」，資料庫記錄「這個模組的這個鍵值在各版本的譯文」。

## 資料模型

譯文跟**內容**綁定，版本只是標示內容出現在哪個遊戲版本。「相同內容」＝ `(類型, 模組, 鍵值, 原文)`。

| 資料表 | 說明 |
|---|---|
| `entry` | 某遊戲版本中的一個可翻譯項目：`(kind, mc_version, mod_id, key) → en_us`。`kind` 為 `lang` 或 `patchouli` |
| `translation` | 掛在 entry 上的譯文，每個來源最多一筆（唯一：`entry_id + source`）；`review_status`（`unreviewed`／`reviewed`／`legacy_unknown`）與來源各自獨立，任何來源都可標為已審核；非人工來源沒有狀態時視為未審核 |
| `effective` | 每個 entry 依已審核狀態與來源優先序選出的生效譯文，並帶出人工審核狀態；寫入時維護，讀取不必重算 |
| `history` | 手動儲存、人工審核、批次取代、AI 舊譯文重翻與還原的異動記錄（保存舊人工譯文、checker、審核狀態及修訂序號；同步版本共用 `batch`） |
| `src_change` | 「鍵值相同但原文已變動」而略過的記錄 |
| `scan_run` | 掃描記錄 |

來源代碼：0 AI 機翻、1 模組自帶繁中、2 簡中轉繁（OpenCC `s2twp`）、3 釘宮翻譯組、4 i18n 轉換、5 自訂補充、6 人工。舊設定名稱「町宮字幕組」仍解析為來源 3。
預設優先序：人工 > 釘宮翻譯組 > 自訂 > 自帶繁中 > i18n > 簡中轉繁 > AI。已審核人工譯文與舊資料中具 checker 的譯文維持校驗優先；未審核的人工譯文依一般來源優先序排序；審核狀態獨立於來源，已審核的譯文先於其他來源的未審核譯文。

### 掃描時的清理規則（與語系合併一致）

jar 自帶的 `zh_tw`／`zh_cn` 與「語系合併」使用同一套判斷與函式（`lang_merge_dict.contains_cjk`、
`text_processor.apply_replace_rules`、`recursive_translate_dict`）：

1. 只有**含中文（CJK）**的值才算譯文；`zh_tw`／`zh_cn` 裡只是英文複本的條目不匯入。
2. `zh_tw` 含中文 → 套用「替換規則」後存為「模組自帶繁中」。
3. 沒有繁中、`zh_cn` 含中文 → OpenCC（`s2twp`）轉繁並套用替換規則，存為「簡中轉繁」（簡中原文一併保留）。
   Patchouli 手冊的譯文會先和同書 `en_us` 比對格式；頁數、欄位不同或物品欄位仍是舊版 NBT 寫法時，視為 mod 改版後沒跟上的過時譯文，這個檔案不匯入 `zh_tw`／`zh_cn`（原文照常匯入）。
4. 原文（`en_us`）用翻譯流程的抽取規則（`extract_translatables`），所以資料庫的條目與機器翻譯要翻的條目一致。

固定文字規則的原子模式會把規則目的詞視為已轉換詞組，避免目的詞內部或相鄰替換片段的交界再次命中來源詞。若目的詞完整等於另一條來源詞，則沿著這種精確鏈收斂到最終譯名；目的詞內部只部分包含的來源詞不會覆寫規則指定的 `to`。需要逐條串接規則時，請明確使用 `cascade=True`。比目的詞更長的來源詞仍會優先套用（例如 `鑽石礦石 → 鑽石礦` 不會因為以「鑽石礦」開頭而被略過）。因此「兩個相鄰目的詞交界剛好形成更長來源詞」時，重複處理同一份結果可能再次命中；替換結果不應再當成原始文字重新處理一次。

替換規則在**掃描當下**套用（可在掃描頁關閉「套用替換規則」）；之後再改規則不會回頭改已存入的譯文。

### 匯入翻譯 ZIP（已翻譯內容）

掃描頁的「匯入來源」可切換成**翻譯 ZIP**（可選單一 ZIP 檔，或放有 ZIP／jar 的資料夾）。這類來源的 `lang/zh_tw` 視為已翻譯：

- **不判讀、不清理、不套替換規則，逐字匯入**：lang 檔的每個字串都收（包含沒有中文的值）；
  Patchouli 書籍沿用欄位名稱規則（只看欄位名，不看內容），並略過 `namespace:id` 形式的資源引用。
- **譯文來源標記**可選（預設「自訂補充」；也可選釘宮翻譯組、i18n 轉換、模組自帶繁中、人工）。
- ZIP 內任何位置的 jar 也會掃描；`assets`／`data` 可以在路徑的任何位置（例如 `pack/1.20/assets/<模組>/lang/zh_tw.json`）。
- **ZIP 沒有 `en_us` 時，原文先留空（原文未知）**：這些條目暫時不會被翻譯流程命中，也不會跨版本同步；
  之後掃描同版本的 jar（或機器翻譯寫回）取得原文時會自動補上，不算「原文已變動」。反過來先掃描 jar 再匯入 ZIP，譯文會加到既有條目（另一個來源）。
- 仍是只新增、不覆蓋：同一條目同一來源已有譯文就跳過。

**「判斷並清理英文內容」開關**（兩種來源都有，預設開）：開＝英文只匯入機器翻譯會翻的條目（略過技術 ID、過短字串等）；關＝所有英文字串逐字匯入。

### 身分（`translation_db/identity.py`）

- **lang**：`assets/<模組>/lang/en_us.json` 的頂層鍵值。
- **patchouli**：`(assets|data)/<模組>/<書籍目錄>/…/<語言>/…/檔案.json` 內的欄位，鍵值為
  「去掉 assets/data 與語言資料夾的相對路徑 + `#` + JSON 路徑」。書籍放在 `assets` 或 `data`、不同語言資料夾，都得到相同身分。
- 1.12 以前的 `.lang` 格式**不處理**。

## 寫入規則

| 動作 | 規則 |
|---|---|
| **掃描 jar** | 只新增、不覆蓋。條目已存在就跳過；既有條目缺少的譯文來源會補入；原文已變動（鍵值相同、原文不同）只記錄到 `src_change`，不改動 |
| **AI 翻譯寫回** | 只新增、不覆蓋（已有 AI 來源就不動）。目標版本沒有條目時直接建立；**其他版本中原文相同、完全沒有譯文的空白也一併補上**。快取命中的譯文也會補進資料庫 |
| **手動儲存** | 新建或修改譯文寫入來源 6，標為未審核（生效來源變成人工）；同一條目其他來源上譯文不同的「已審核」標記會退回未審核（否則已審核譯文仍會勝出，儲存看起來沒生效），批次尋找與取代同樣處理，還原時一併復原；文字相同時不改變現有審核狀態。可同步其他版本中原文相同的條目 |
| **審核** | 把目前生效的那一列標為「人工已審核」，生效來源不變（釘宮翻譯組審核後仍是釘宮翻譯組）；卡片上來源與審核狀態是兩個標籤。審核與還原都記錄是哪個來源的哪一列被改。操作前預覽會同步及略過的版本；開啟同步時，原文相同的其他版本即使目前譯文不同，也會改寫為此譯文並標為已審核（歷史記錄被取代的譯文，可還原），已審核相同譯文者略過；可選擇只審核目前版本 |
| **批量審核** | 選一個版本與其「目前生效來源」，把該版本中尚未人工審核、有譯文的條目逐筆當作單筆審核處理（只標審核狀態、記錄歷史）；任何來源都只列尚未審核的條目。可只限格式檢查通過的條目（預設）、可排除個別條目、可同步其他版本（預設關閉，規則同審核）。確認時重算範圍並與預覽逐欄比對，不同就整批拒絕；同一批次共用一個 batch，可整批還原（之後又被改動的條目不覆蓋） |

來源 6 的既有資料無法判定歷史上是「儲存」還是「審核」，因此以 `legacy_unknown` 記錄，畫面上同樣顯示「人工已審核」。審核不增加來源代碼，也不改變生效來源。開啟舊資料庫時（schema v6）會先備份（`*.pre-schema-v6-*.bak`），再把「來源 6、已審核」的列移回原來源：只處理「整個歷史只有一次審核、該次審核寫入的版本就是人工列現在的版本」且譯文與另一來源相同的列（有手動儲存、批次取代或其他操作紀錄的一律保留），目標來源依你儲存的來源優先序選擇；該來源的列標為已審核、來源 6 的列移除（歷史記錄為 `review_migrate`）。無法證明來源的列一律維持人工來源、已審核。翻譯 ZIP 若只有簡中，轉繁後仍歸在你選擇的來源。審核操作在核心資料層比對目前顯示文字、來源、checker、審核狀態與完整版本預覽（CAS）；畫面資料過期時拒絕寫入，要求重新整理。編輯框必須仍與選取的生效譯文完全相同才可審核。

## 特殊字元（換行、格式碼、前後空白）

資料庫與介面**逐字保存**譯文：真正的換行、字面的 `\n`、`§` 格式碼、`%s`／`%1$s`、`{0}`、Patchouli 的 `$(…)`、前後空白都不會被修剪或改寫
（空白只用來判斷「是不是空的」）。條目校對頁：

- 原文與譯文的輸入框會原樣顯示換行；清單預覽把真正的換行顯示成 `¶`（字面 `\n` 照原樣顯示）。
- 譯文與原文的換行、`§` 碼、`%s` 類佔位符、`$(…)` 數量不一致時，輸入框下方會提醒「少了／多了幾個」。
- 譯文含 `§` 時顯示顏色預覽；前後有空白或換行時提醒「儲存時會原樣保留」。

## 條目校對的狀態篩選

「全部／未翻譯／版本不同／原文已變動／翻譯與原文相同／人工／其他譯文」是即時計算的分類條件。人工審核狀態另由「人工審核狀態」篩選，依目前生效來源與 `review_status` 套用相同的清單、筆數和分頁條件。

- **翻譯與原文相同**：目前生效的譯文（已套用來源優先序，與畫面顯示的相同）與 `en_us` **逐字完全相同**，且兩者都非空。
  只是陳述資料特徵：專有名詞、縮寫（例如 `Minecraft`、`JEI`、`RF`）本來就可以不翻譯，不代表翻譯錯誤或未翻譯。
  這類條目仍算「已翻譯」、不屬於「未翻譯」；寫入資料庫與翻譯快取的行為也與其他譯文完全相同。
  比較不做大小寫、空白或 Unicode 正規化。
- 條目校對的「目前生效來源」篩選使用 `effective.source`；較低優先序的 AI／JAR／自訂來源 row 即使仍保存在 `translation`，也不會讓條目命中該來源篩選。審核不改變 effective 來源，因此審核過的 AI 條目仍會出現在 AI 來源篩選；「審核狀態」篩選（未審核／人工已審核）與來源篩選可組合。非人工來源的譯文被改寫時，舊的已審核標記會自動清除；AI 特殊字元自動修復同樣退回未審核（若退回後會讓別的來源接手生效，該筆保留原文、不修復），在修復審查裡人工確認草稿則會把該來源標為人工已審核。
- 右側「各來源譯文」仍列出所有已保存來源；主清單篩選只看 effective，與明細中的歷史／低優先序 row 各自有明確用途。
- 「其他譯文」表示目前有生效譯文且來源不是人工；其原有分類條件不變，與「人工」互斥。
- 篩選可與搜尋、模組、類型及狀態組合；總筆數與分頁列使用同一組條件。

### 進階時間與品質篩選、批次字面取代

- 進階篩選預設收合，提供條目匯入、來源首次匯入、目前譯文更新與人工操作時間；台灣本地日期會轉成 UTC 半開區間 `[start, end)`，自訂區間含起訖日。舊資料缺少來源首次匯入時間時保留為未知，可包含、排除或只看未知。
- 時間篩選使用條目時間、目前生效來源的 `translation.created_at`／`updated_at`，或以 `EXISTS` 查詢符合操作類型的 history；不會因一個條目有多筆 history 而重複出現在清單。時間排序固定將未知時間放最後，並以 entry id 穩定排序。
- 品質分析只檢查目前生效譯文，與編輯提示共用 token 分析器；識別 `%s`／`%1$s`、`{0}`、Minecraft `§` 色碼、Patchouli 巢狀提示、字面 `\\n` 與實際換行。品質條件在分頁前套用，筆數與清單結果一致。原文未知、未翻譯、token 不一致、相符與前後空白是分開狀態。進階篩選的「品質狀態」另有「疑似學名文字」：列出英文原文像學名（key 含 `latin`／`scientific` 等提示，或值含 ×、var.、subsp.）的條目，方便直接在條目清單檢查它們的譯文；它不會連線查詢。
- 「批次取代」依目前所有篩選版本，逐字替換生效譯文，不修剪空白，也不修改 AI 快取或替換規則。預設只處理目前版本；勾選跨版本時，僅納入原文、生效譯文、來源及審核狀態完全相同的其他版本。每頁最多顯示 50 筆預覽，列出英文原文、資料庫來源名稱與代碼、人工審核狀態、品質 token 數量及前後空白風險；可取消個別根條目，並可檢視略過原因與跨版本標記。長文字可選取並換行。
- 批次取代預覽裡改變「個別排除」、全選／全不選或「僅處理已勾選的根條目」時，會自動用新範圍重新預覽，被排除的根條目仍留在清單原位（灰色，可再勾回）；改變尋找文字、取代文字或同步選項則需要手動按「產生預覽」。
- token／空白品質惡化須對目前精確預覽計畫額外勾選確認；重新預覽、變更文字／同步選項、根條目選取或處理範圍都會清除舊確認。背景作業摘要僅保留狀態與筆數，完整計畫透過綁定作業 session 和 generation 的單次結果通道交付；對話框關閉或結果過期時會丟棄該通道。
- 批次執行前在同一寫入交易內重算範圍並逐筆比對 effective/manual 修訂序號；任一快照變動便整批拒絕。成功時只寫來源 6 並標為未審核，保留其他來源及完整 history。history 提供「整批還原」；還原逐筆 CAS，後續已修改的資料會略過並回報數量。

### 學名候選掃描

條目校對頁的「掃描學名」會依目前選取的版本、模組與類型，讀取 `entry.en_us` 找出符合學名格式的候選值。掃描只讀取資料庫，不會新增或修改翻譯。

- 「掃描候選」先做本地判斷，不會因開啟視窗就發出網路請求。預設只收 key 含 `latin`、`scientific` 等提示且格式像學名的條目，一般介面文字與物品名稱不會被當成候選；若學名放在沒有這類提示的 key，勾選「包含沒有學名 key 的候選」即可改為只看格式（雜訊較多）。
- 每筆候選都有「查詢」按鈕；「查詢全部候選」會依序使用學名快取與中文 Wikipedia/MediaWiki API，查到的中文名稱只寫入既有學名快取。查無的結果也會記在快取，所以掃描時查過的候選（不論找到或查無）都直接顯示結果，批次只查其餘的；查無的候選可按「再查一次」重新查詢維基百科。
- 查詢中視窗底部會出現「背景執行」：按下後視窗收起、查詢繼續，可以先回去校對，進度顯示在頂列的任務膠囊，完成或停止時會跳出摘要提示。再次開啟「掃描學名」會接回進行中的查詢。按「關閉」則會停止查詢並關閉視窗。
- 「開啟條目」會關閉視窗並跳回該筆條目的編輯器，方便確認模組與鍵值後再決定是否翻譯。
- 查詢中可按視窗裡的「停止查詢」、「關閉」或從頂列任務取消，已查完的結果會保留；「背景執行」與「開啟條目」不會停止。遇到維基百科限流或連續失敗時批次會自動停止，失敗的候選可按「重試」。
- 找不到頁面會顯示「找不到對應條目」（網路失敗不會顯示成這個結果），不會把英文值自動改寫成譯文，也不會寫入 Mod 資料庫。
- 亞種、變種、品種這類三段式名稱（例如 `Fagus sylvatica purpurea`）查無時，會另外查前兩段的物種名稱，顯示成「上一層物種 Fagus sylvatica：歐洲山毛櫸（僅供參考）」。變種的正確譯名通常不同，條目校對的「學名」分頁可按「套用參考名稱」帶入譯文框後再自行修改。上一層物種若查詢失敗（例如限流）或還沒查過，會顯示原因與「補查上一層」；批次查詢遇到這種限流會自動停止，之後再按「查詢全部候選」會只補查上一層物種，不會重查原本的名稱。
- 候選數量不設上限，列表底部用頁碼切換（每頁 50 筆）；掃描走資料庫篩選，大型資料庫也只需一兩秒。
- 條目校對右側的建議區有「學名」分頁：目前條目原文像學名時，會顯示查到的中文名稱，按「套用」把名稱帶入譯文框（不會自動儲存，仍需按「儲存」或「審核」）；還沒查過可直接按「查詢維基百科」，失敗時可「重試」（一定會重新連線，即使之前有查無紀錄）；背景查詢查到目前條目時會即時顯示。在掃描視窗按「開啟條目」會直接切到這個分頁。
- 線上查詢有速率保護：每筆查詢前等待 0.5 秒、失敗重試 3 次並遵守伺服器的 Retry-After；遇到限流或連續失敗時批次自動停止，已查到的名稱都會留在本機快取。

### 各版本有效來源統計

總覽依 `effective.source` 逐來源統計，再按 `unreviewed`、`reviewed`、`legacy_unknown` 分桶，未翻譯獨立計數。查詢以一次 `GROUP BY mc_version, source, review_status` 取得所有版本，不會依版本或來源逐筆查詢。圖例只列出目前資料庫中實際出現的有效來源；零筆來源不顯示，未翻譯固定列出。圖例和堆疊順序依目前來源優先序排列，但來源代碼始終是穩定身分。

### 舊 AI 同原文譯文重翻

Mod DB 批次機翻預設只處理沒有生效譯文的條目，並透過 `write_back()` 只新增、不覆蓋。要修復既有資料，使用批次機翻頁的「舊 AI 譯文修復」：先依目前版本／模組／筆數上限預覽，再明確確認執行。

- 候選必須是目前 `effective.source = SRC_AI`、`effective.zh_tw = entry.en_us`，且兩者非空。人工或任何其他有效來源不會入選。
- 修復直接呼叫 `translate_batch_smart()`，不走 DB/cache hit；「譯文與原文相同時重新確認」仍依 `retry_same_as_source` 設定照常執行一次。
- 僅以專用 compare-and-set API 更新該 entry 的 `SRC_AI` 列；更新前再次確認舊值和 effective AI 條件。競爭期間已變更的資料會跳過。
- 成功更新寫入 `history.action = ai_retranslate`，並刷新 `effective`。不會同步或填補其他版本；token/格式檢查或 API 失敗時保留舊譯文。
- 翻譯快取一律寫入（`enable_cache_saving` 關閉時除外），只在 DB 更新成功後用現有 Cache API 更新該項目；「每次寫入新快取分片」關閉（預設）時寫入編號分片，開啟時另存獨立的時間戳分片。此修復不刪除舊 Cache，也不改一般 Cache 命中規則。

此流程不增加資料庫狀態欄位或 migration；一般 `write_back()` 與其他翻譯呼叫者的只新增、不覆蓋契約維持不變。

一般批次機翻和舊 AI 重翻共用四張統計卡。一般模式顯示沿用其他版本、AI 寫入、特殊字元不一致與尚未翻譯；舊 AI 重翻模式顯示候選、成功更新、有效回應仍相同及範圍內剩餘候選。重翻格式不符、競態跳過、失敗及快取未同步留在詳細摘要，不能當作「仍相同」或成功更新。任務中以當次 `TaskSession` 的部分摘要更新數字；剩餘候選只在任務結束後顯示，取消和失敗保留部分結果與狀態。

## 與翻譯流程的整合

`translate_directory_generator`（機器翻譯與一鍵流水線）的查詢順序為 **資料庫 → 翻譯快取 → AI**：

1. 資料庫：目標版本自己的譯文（原文須與資料庫 `en_us` 完全一致）；沒有時，沿用其他版本中原文相同的譯文（版本最接近者；可關閉）。
2. 快取、AI 與先前相同。
3. 翻譯完成（含取消前已完成的批次）才寫回資料庫；`dry-run` 不寫入；沒有翻成功而以原文回填的項目不寫入。

資料庫檔案不存在、設定關閉、或沒有指定目標版本時，整個功能等同不存在（翻譯流程不會建立資料庫檔案）。
### 手冊與指南的辨識

手冊（Patchouli 類）的欄位**不看欄位名稱**，只看值的形狀：資源 id、旗標、錨點、路徑、網址、數字、色碼、模板變數（`#tier#`）、小寫或駝峰識別字、物品堆疊與 NBT 片段、已是中文或沒有英文字母的字串都不翻；`multiblock` 版面子樹整段略過；指向語言檔的鍵（`book.mod.entry`）不在手冊內翻譯。
不必設定手冊資料夾：掃描 jar 時，設定的資料夾名稱（`lm_translator.patchouli.dir_names`，任何深度的資料夾名稱都算，例如 `guide`、`ae2guide`）之外，會依內容再找出手冊與指南——JSON 有 `pages`／`landing_text`／Patchouli 規格資料夾（`categories`、`templates`）結構，`.md`／`.txt` 是英文敘述文字（有 front matter，或段落像句子）。匯入選項「包含手冊、指南與進度文字」關閉時，手冊、指南、進度文字與依內容辨識都不執行，只匯入語言檔。判斷以資料夾為單位抽樣讀取，有獨立的讀取上限，用盡時只停止判斷，不會讓整個 jar 失敗。`textures`、`models`、`worldgen`、`recipe` 等 Minecraft 規格的資料夾、`README`／`CHANGELOG` 類文件與其他語系資料夾（`ja_jp`、`_ru_ru`）不會被當成原文。
指南（`.md`／`.txt`）以段落為單位匯入，鍵值是 `檔案路徑#段落序號`；只有標籤、Markdown 註解（`[//]: #`）、授權條款、設定內容（多數行是 `key: value`）、名字清單（八行以上、每行一到三個字、沒有句末標點，或一行用逗號隔開八個以上短名稱）、結構資料（多數行只有標籤或符號、可見英文字不到六個，如 Ice and Fire 的版面指令）、程式碼範例（多數行是 Lua 之類的程式碼）、MDX 的 `import`／`export` 行和 `TODO`／Lorem ipsum 佔位字的段落不匯入（段落序號不因此位移）；Patchouli 手冊的佔位字（`TODO`、`[TODO: … goes here]`、Lorem ipsum）同樣不匯入。`.mdx` 與 `.md` 同樣處理，內文中的 `---` 水平線不會被當成 front matter。語系資料夾或檔名後綴（`_zh_tw`、`_zh_cn`、`ru_ru`、`de`、`pt-br`）與語言檔共用同一套辨識，其他語言不匯入。匯入翻譯 ZIP 時，名稱沒對上的資料夾也會依內容辨識，只有繁中／簡中譯文（沒有英文原文）的指南與手冊同樣收進來，原文先留空；內容辨識對每個檔案各自驗證，同資料夾的設定檔不會沿用手冊的結論。舊版 `.lang` 與語系合併共用同一個解析器（無 `=` 的行接在上一筆後面、值去掉首尾空白）。`_zh_tw`／`_zh_cn` 資料夾裡的譯文在段落數相同時才配對；原文整頁只有一個區塊時，整頁譯文對整頁原文。指南條目在條目校對頁有兩項專用功能：譯文的 Markdown 標記（標題／清單／引用前綴、`**`、行內程式碼、連結目標）和 `<br>`、元件標籤與原文不一致時，譯文框上方顯示「指南標記與原文不一致」；「Minecraft 樣式預覽」改用 Markdown 近似預覽（標題加粗放大、粗體、斜體、行內程式碼、連結文字、清單與引用前綴、`<br>` 換行），元件標籤淡色原樣顯示。預覽只是近似，不等於遊戲內 GuideME 的實際畫面。LM 翻譯指南時用同一套標記比對，不一致的段落保留原文。譯文的行數比原文的文字行數多時，多出的行併進最後一行，不會因為寫回原檔而遺失後半句。

### 其他會匯入的內容

- 舊版 `key=value` 語言檔（`assets/<模組>/lang/en_US.lang`、`zh_CN.lang`…）：與 `.json` 語言檔同一個身分；同一個語系兩種格式都有時用 `.json`，`assets` 與 `data` 都有時用 `assets`。`data/<模組>/lang/<語系>.json` 也算語言檔。
- 進度（`data/<模組>/advancement(s)/…`）：只匯入 `display.title`／`display.description` 寫成**字面文字**的進度（類型 `advancement`）；寫成 `{"translate": "鍵"}` 的由語言檔負責，沒有顯示文字的配方解鎖進度不匯入。鍵值不含 `advancement`／`advancements` 資料夾，跨版本是同一個鍵。
- 書本根目錄的 `book.json` 不匯入：Patchouli 官方文件說明 `book.json` 必須放在原位，資源包能否覆寫它沒有確認。

Patchouli 與 lang 走同一個流程，只是身分不同。FTB Quests / KubeJS / Markdown 不使用資料庫。

### 資料清理（總覽頁「資料清理」）

清理目前規則判定「不是要翻譯的內容」的舊條目（指南：只有標籤或符號、Markdown 註解、授權條款、設定內容、名字清單、`TODO`／Lorem ipsum 佔位字；Patchouli：多方塊圖案列、佔位字、不是顯示文字的字串）。檢查檔的每個項目除了編號，類型、模組與鍵值也必須與資料庫目前的條目一致，不一致就略過（換了資料庫複本或編號被改動時不會刪到別的條目）。語言檔與進度文字只用保守規則（語言檔另外排除 `_` 開頭的翻譯者備註鍵、`language.code`、`.color` 色碼、`SEED_OIL_BUCKET` 或 `tube_module` 這類常數／識別字與單獨網址；`TODO`／Lorem ipsum 佔位字、只有符號或數字而不含 `%s` 之類格式碼的字串、進度內容就是欄位名稱如 `Description`），不判斷內容語意：小寫單字（`on`、`off`）和含格式碼的字串都是正常譯文，會保留。

1. **匯出檢查檔**：選版本後按「匯出檢查檔」，在資料庫檔案旁的 `cleanup_reports` 資料夾寫出 JSON（只讀資料庫、不刪任何東西）。檔案內有每類的筆數與逐筆項目（編號、類別、模組、鍵值、原文）。
2. **自行檢查**：用編輯器開啟，不想刪的項目整個移除，或把 `delete` 改成 `false`（只有明確的 `true` 才會刪除；缺少 `delete` 或寫成字串 `"false"` 的項目會略過並計入略過原因）。
3. **依檢查檔清理**：選檔案先「預覽刪除」，會依**目前資料與規則**逐筆重新檢查：條目已不存在、原文已變動、現在判為正常內容、或已有譯文／歷史紀錄的都會略過並列出原因；確認後才刪除。
4. **還原上次清理**：刪除前整批（含關聯的譯文、生效譯文與歷史）存進 `cleanup_batch`，可整批還原；重新掃描後已有同一條目的會略過、不覆蓋。

有任何譯文（包含模組自帶繁中）、生效譯文或歷史紀錄的條目一律不列入，所以不會刪到你翻過、審核過的內容。

## 設定（`translation_db`）

| 設定 | 預設 | 說明 |
|---|---|---|
| `enabled` | `true` | 翻譯時使用資料庫（機器翻譯頁可個別覆寫） |
| `path` | `mod_translation.db` | 相對路徑以資料目錄為基準 |
| `version` | 空 | 預設目標版本；**沒有指定版本就不會查詢或寫回**（機器翻譯頁可個別填寫） |
| `cross_version` | `true` | 允許沿用其他版本、原文相同的譯文 |
| `write_back` | `true` | 翻譯結果寫入資料庫 |
| `sync_manual` | `true` | 手動儲存時同步其他版本（頁面上也可個別關閉） |
| `priority` | 見上 | 來源優先序（每行一個顯示名稱或穩定代碼，例如 `builtin:subtitle`、`custom:100`）；設定頁顯示來源名稱，`config.json` 會將已登錄來源保存為穩定代碼；舊名稱仍依資料庫登錄解析 |

### Schema 升級

Schema v3 增加每個來源譯文的首次匯入時間與單調修訂序號，以及 history 的前後修訂快照。升級 v1 會先依序建立 v2 與 v3 備份；升級 v2 會先建立 `*.pre-schema-v3-<時間戳>.bak`。舊資料的 `translation.created_at` 保留為 `NULL`，不推測匯入時間。migration 在單一交易中完成；唯讀開啟舊資料庫不執行 migration，時間欄位會顯示未知。備份檔應和資料庫一樣納入使用者自己的備份政策。

## 安全與失敗契約

- **只動自己的資料庫**：開啟既有檔案前先以**唯讀**連線驗證（`meta.schema_version` + `entry` 欄位）；設定指到其他 SQLite
  或不是 SQLite 的檔案時，**拒絕開啟、不建立任何資料表、不改 journal mode**（功能停用並記錄警告）。
  `create=False`（翻譯流程）還不會把空檔案初始化；資料庫版本比程式新時同樣在唯讀階段就拒絕（不開任何可寫連線，檔案位元組與 journal mode 都不變）。
- **掃描失敗不寫入部分資料**：一個 jar／ZIP 讀取失敗（損毀、單一成員過大、超過累計預算）時，**整包不寫入**，
  在結果中算「失敗」並顯示原因；內嵌 jar 本身損毀、或 jar 檔本身超過單檔上限時只略過它（外層內容保留），並計入「略過的內嵌 jar」；
  若遞迴掃描過程觸發 archive／整棵樹的安全預算，則整個頂層 archive 視為失敗（fail-closed）。
- **ZIP bomb 防護**：每個 archive 有自己的讀取預算，另外整棵遞迴樹（外層 + 所有內嵌 jar）共用一個總預算，
  壓縮率很高的內嵌 jar 不能放大總解壓量；內嵌 jar 本身的讀取也計入父層預算。
- **取消**：掃描在每個解壓區塊（64KB）都檢查取消，大型 jar 也會立刻停止，並且不寫入該 jar。

## 程式結構

```
translation_tool/translation_db/
  schema.py      資料表、來源代碼、連線（WAL）
  models.py      對外資料結構
  identity.py    路徑 → (類型, 模組, 鍵值)；get_by_path
  repository.py  所有 SQL：掃描寫入、手動同步、還原、寫回、查詢
  scanner.py     讀 jar（含 META-INF/jarjar 內嵌 jar、Patchouli 書籍）並寫入
  resolver.py    翻譯流程用的查詢（TranslationResolver）與寫回緩衝（WriteBackBuffer）
  settings.py    讀取 translation_db 設定、開啟資料庫
  cleanup.py     資料清理：匯出檢查檔、預覽與刪除、整批還原
translation_tool/core/lm_translator_db.py   目錄翻譯的銜接（開啟、分流、寫回）
app/services_impl/moddb_service.py          View 取用資料庫的服務層（View 不直接 import 引擎）
app/views/moddb_view.py + app/views/moddb/  總覽 / 條目校對 / 掃描匯入
```

學名候選掃描的讀取服務位於 `app/services_impl/moddb_species_service.py`，
`app/views/moddb/species_dialog.py` 負責候選列、逐筆查詢與跳回條目編輯器，
`app/views/moddb/species_bulk_lookup.py` 負責背景批次查詢；它們都不直接寫入翻譯資料表。

入口：側欄「資料庫」群組的「Mod 資料庫」、`Ctrl+P` 快速跳轉、工作台卡片、機器翻譯頁與設定頁的選項。
掃描使用 `zip_safety` 的讀取預算（防 ZIP bomb），內嵌 jar 最多遞迴 3 層。

## 日誌與錯誤訊息

- **UI 與後台一致**：掃描進度（每個 jar 的結果、失敗原因、略過的內嵌 jar、摘要）同時寫入畫面日誌與後台 log
  （帶 `[Mod 資料庫掃描]` 前綴）；寫入 session 的訊息會標記 `ui_mirrored`，UI log handler 不會重複送進畫面。
  失敗與略過用 `warning`／`error` 等級，「只看警告以上」篩選可用。
- **開不起來就說原因**：設定的檔案存在但不是本功能的資料庫、或版本太新時，總覽、工作台、機器翻譯頁都會顯示
  原因（而不是「尚未建立資料庫」）；掃描也會在日誌寫明。
- **寫入失敗指出對象**：資料庫寫入失敗會帶出 jar 名稱、版本與資料庫路徑；手動儲存／還原失敗在畫面提示並寫後台 log。
- 略過的內嵌 jar 會列出完整路徑與原因，不再只顯示數量。

## 中斷續跑與資料庫選項

- 機器翻譯的 checkpoint 會保存這次任務**實際生效**的資料庫選項 `translation_db: {enabled, version}`
  （解析後的值：畫面欄位留空時存設定檔的版本，不存 null）。
- 續跑時機器翻譯頁會還原這兩個值再開始，**不採用重開後的頁面或設定值**；否則剩餘項目會查詢、
  寫回到不同的版本。上次其實沒有版本（等於沒用資料庫）時，續跑同樣不使用，不會退回目前設定的版本。
- 沒有這個欄位的舊 checkpoint（資料庫功能之前建立）一定沒用資料庫，明確視為停用；checkpoint 版本號不變，
  其餘續跑行為照舊。
- 若續跑時實際使用的選項仍與 checkpoint 不同（例如一鍵流程），會記錄警告，說明剩餘項目依這次的選項處理。
- 資料庫選項 `(enabled, version)`（設定為「下次任務才套用」）**每個任務只解析一次**：開啟資料庫、寫回、
  checkpoint 共用同一份不可變的選擇，任務進行中改設定不會影響這次任務，也不會讓 checkpoint 記到下一個任務的設定。
  停用或沒有版本都解析成「不使用」`(False, "")`。
- 其餘設定（路徑、跨版本沿用、寫回開關、來源優先序）在**資料庫連線建立時**讀取一次，建立後不再變動；
  它們不會寫進 checkpoint，續跑時依當時的設定。若之後要把整組設定做成單一不可變快照，
  可讓一個 `resolve_db_settings()` 產生完整設定再傳給 `open_directory_db()`（目前不需要）。
