# ADR-0006: 模組 × 來源分面與 stat_src 的模組／類型欄位

## 背景

條目頁每次載入都要取得下拉選單的模組與來源選項，以及目前篩選的總筆數。篩選過的清單
（搜尋、審核狀態、來源、無譯文…）在 28 萬條目的版本上，選項與總數各要掃描整個版本
（約 0.1–0.5 秒），沒有快取；同一組篩選下翻頁、換模組、換來源都會重做。版本清單與
來源代碼在每次寫入後也要重新分組整張條目表。

## 決策

- `stat_src` 的主鍵改為（版本、模組、類型、生效來源、審核狀態）；`stats_schema_version`
  為 3，舊庫在可寫開啟時重建。原有的版本／來源讀取端改為加總，版本清單與來源代碼改由摘要取得。
- 新增 `option_facets.py`：一組篩選（拿掉模組與來源）算一次「模組 × 來源」筆數分面，
  導出選項與任何選擇下的總數。條件只含版本、類型、審核狀態、無譯文時由 `stat_src` 彙總，
  其他條件以一次沿 `idx_entry_list_order` 的串流 `GROUP BY` 掃描，依資料世代快取。
- 批量審核與智慧校對的範圍選單使用同一個掃描分面。
- 不採用 FTS5 trigram 做搜尋：在 85 萬筆上建立約 90 秒、增加約 270 MB（只含原文與鍵值）；
  不足三個字元的查詢（常見的兩字中文詞）不能使用；結果很多的常見詞比 LIKE 掃描並未更快；
  還要在每個寫入路徑維護一份文字副本。

## 後果

- 選項與總數在同一資料世代內只算一次；寫入後的第一次載入仍要一次掃描（搜尋、狀態為
  差異／一致／人工／相同的篩選），其餘條件由摘要即時回答。
- 每次條目或生效譯文寫入多更新一個較細的桶並多讀幾個條目欄位，大量寫入約慢 15–25%。
- `stat_summary.verify()` 與 `tests/test_translation_db_option_facets.py` 在每條寫入路徑後
  比對分面與逐列查詢的結果。
