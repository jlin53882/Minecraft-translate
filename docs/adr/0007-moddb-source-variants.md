# ADR-0007: 同一鍵值的其他原文（變體）與流水線查詢

## 背景

`entry` 對 `(類型, 版本, 模組, 鍵值)` 只存一份 `en_us`。模組更新或不同整合包讓同一個鍵值出現
不同原文（例如 `Show Background` → `Background Style`）時，掃描與 AI 寫回都只記錄 `src_change`、
不改主原文，也不寫入譯文。流水線查詢要求原文完全相同，所以這些條目每次都是 `en_mismatch`，
每次都列為待翻譯，AI 翻完也存不進資料庫。

同一個遊戲版本可以有多個整合包（8.5、8.6 都是 1.21.1），各自帶不同版本的模組 jar，所以
「以新原文覆蓋舊原文」會在輪流掃描時來回覆蓋；「人工逐筆接受新原文」則每次模組更新都要重做。

## 決策

- `entry` 維持「一個鍵值一筆、一份主原文」。其他原文存在側表 `entry_variant`，譯文存在
  `variant_translation`；兩張表與 `entry`／`translation` 同形（來源、審核狀態、修訂序號），
  日後要升級成「鍵值＋原文」的完整變體模型時只需搬資料。
- 變體的讀寫集中在 `variants.py`，其他模組只呼叫它的函式，不直接寫這兩張表的 SQL。
- AI 寫回（`TranslationDB.write_back`）遇到原文與主原文不同：主原文不動、照舊記錄 `src_change`，
  譯文存成該條目這份原文的變體（只新增、不覆蓋；不補其他版本的空白）。
- 流水線的 `TranslationResolver`（一鍵流水線、機器翻譯頁、語系合併 `MergeDbFill` 與指南流水線都經由它）透過 `load_mod`／`load_mod_for_priority` 讀到變體列，格式與主原文
  相同、使用同一套來源優先序（沒有指定優先序時取資料庫 `meta` 的共用優先序，與 `effective` 投影一致），
  `lookup` 依原文選出相同的那一份。流水線開啟跨版本沿用時，變體與主原文一樣可能成為跨版本命中；
  `write_back` 不把變體補到其他版本的空白。
- 條目清單、統計、審核、跨版本沿用、版本差異審核與 `jar_english` 只看 `entry`／`effective`，
  不受變體影響。
- 不自動把舊譯文沿用到新原文：舊譯文是照另一段原文翻的，語意改變時會誤導。
- 變體的 AI 譯文不需要審核即可被流水線使用，與一般 AI 譯文相同。

## 後果

- 原文變動的條目在第一次 AI 翻譯後即可由流水線查到，不再每次列為待翻譯。
- 變體譯文目前不會出現在條目清單與統計；條目詳情的呈現、審核、掃描登記與回填
  既有 `src_change`、清理與重複合併時的快照／還原由後續變更處理。這之前，清理刪除條目時
  變體隨條目一併刪除（外鍵 `ON DELETE CASCADE`），還原不會帶回變體。
- 每個變體記錄 `first_seen`／`last_seen`，供日後清除不再被掃到的舊原文。
- schema 版本升為 18；`change_tracker` 追蹤兩張新表，外部 SQL 寫入同樣會使統計快取失效。
