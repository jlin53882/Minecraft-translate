# ADR-0005：品質篩選改讀每個條目的品質旗標

- 日期：2026-10-15
- 狀態：實作
- 基準：`88adb31`（ADR-0004 的衍生欄位）

## 背景

條目清單的品質篩選（相符、token 不一致、疑似學名、學名格式、前後空白、未翻譯）先以 SQL
縮小候選，再對每個候選列執行 `matches_quality`。候選常是整個版本：70 萬條目的備份上，
品質規則
（token 掃描、學名正規表示式）只能在 Python 判斷，無法直接寫成 SQL 索引條件。

## 決策

### `entry.qflags`（`translation_tool/translation_db/quality_flags.py`）

- 每個品質狀態一個位元：未翻譯 1、前後空白 2、token 不一致 4、相符 8、疑似學名 16、
  學名格式 32；值與 `matches_quality(en_us, 生效譯文, QualityFilter(status=狀態), key)`
  相同。原文未知仍以 `en_us=''` 篩選，不佔位元。
- 每個位元一個部分索引 `entry(mc_version, mod_id, kind, key, id) WHERE qflags & 位元`，
  欄位順序與清單預設排序相同；另有 `entry(id) WHERE qflags IS NULL` 找出待重算的條目。
- 觸發器只把受影響的條目設為 `NULL`（待重算）：生效譯文新增、刪除、文字或條目改變，
  條目的原文或 key 改變，以及帶入舊旗標值的條目新增（還原清理快照）。新條目預設為 `NULL`。
- `TranslationDB._tx` 在提交前呼叫 `settle()`，以 `quality.py` 重算所有待重算條目，
  所以品質規則只有 Python 一份，不在 SQL 重寫。整批重建生效譯文不暫停這些觸發器：
  只有文字真的改變的列會觸發，成本與改變的條目數成正比；暫停後全部重算則每次都要
  約 2.5 秒計算 70 萬列。
- `meta.quality_schema_version` 是旗標定義版本（品質規則改變時遞增），
  `quality_valid='1'` 表示可用。可寫開啟時缺少、版本不同或觸發器定義不同，就在一個交易內
  安裝結構並把全部條目設為待重算，再每 2 萬筆提交一次地重算；中斷後下次開啟接續。

### 讀取端

- `_quality_filtered_page` 先檢查旗標可用（版本、有效旗標、沒有任何待重算條目）。可用時，
  方向與類別都是「全部」的六種狀態直接以 `e.qflags & 位元` 走一般的分頁與筆數查詢
  （`_paged_entry_rows`、`_cached_count`），不再逐列判斷。
- token 不一致另選方向或 token 類別時仍逐列判斷，但預篩改為 `e.qflags & 4`，只檢查
  旗標為不一致的條目；批次取代的品質範圍同樣用旗標預篩。
- 有待重算條目時（舊版程式等外部寫入者、同一寫入交易中尚未提交的改動）、旗標無效或
  唯讀開啟沒有欄位的舊資料庫，改用原本的 SQL 預篩加逐列判斷，結果相同。

## 取捨與風險

- 每次寫入交易多一次待重算索引查詢；有改動時每個條目多一次 Python 品質判斷與一次索引更新。
  全部生效譯文都改變的整批重寫約多一倍時間（每列都經觸發器標記再重算）。
- 外部寫入者（舊版程式）寫入後到本程式下一次寫入或開啟之間，品質篩選走較慢的逐列判斷。
  讀取端在檢查待重算與實際查詢之間沒有包在同一個讀取交易時，外部寫入者恰好在兩者之間
  提交，該頁可能用到舊旗標；本程式自己的寫入在提交前已重算，不受影響，條目清單頁的背景
  讀取本身包在讀取交易中。
- 改變 `quality.py` 或學名規則的判斷結果時必須遞增 `quality_schema_version`，否則已存的
  旗標與新規則不同。

## 正確性保護

`tests/test_translation_db_quality_flags.py` 在四個版本上比對六種狀態 × 多種篩選
（模組、來源、審核狀態、狀態、關鍵字）× 四種排序的完整條目順序、總數與多個偏移，
與強制逐列判斷的結果相同；也測試方向／類別篩選、外部寫入留下待重算時退回、寫入交易內
讀取、逐一移除每個觸發器時至少一步驗證失敗、分頁與筆數查詢沒有暫存排序、唯讀舊資料庫
退回與可寫開啟安裝、分批重算中斷後接續、無效旗標與重建、定義版本改變時全部重算。
`tests/test_translation_db_stat_summary.py` 的共用檢查在每條寫入路徑後呼叫
`verify_quality_flags()`。
